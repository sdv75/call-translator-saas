# Экспериментальный аудиопротокол

По умолчанию `/ws` возвращает 503, без резервирования баланса. Для локальной разработки существует явный `CT_EXPERIMENTAL_AUDIO=1`. Это не разрешение продавать непроверенный перевод и не подтверждение точности биллинга. `/api/calls` POST остаётся выключенным: создание выполняется внутри WebSocket, чтобы звонок жил ровно с соединением.

После WebSocket-handshake клиент за 5 секунд отправляет JSON `{"token":"<device credential>","source":"ru","target":"en"}`. Передавать credential в URL запрещено. Source — язык пользователя, target — язык остальных участников. Начальные адаптеры принимают en/ru/uk, но наличие этих кодов ещё не означает готовность соответствующих локальных голосов. Браузерная cookie не заменяет credential устройства для аудио.

Сервер проверяет credential, лимит звонков и баланс, резервирует максимум 5000 мс, открывает два STT-потока и только затем сообщает `{"type":"ready",...}`. Второй звонок не меняет первый.

Каждое бинарное сообщение — ровно 641 байт:

| Байты | Значение |
| --- | --- |
| 0 | 0 — outgoing (микрофон пользователя), 1 — incoming (аудио собеседников) |
| 1–640 | 320 PCM16 little-endian mono samples, 16kHz, 20 мс |

Время назначает сервер: первоначальная привязка к моменту получения и последовательные аудиокурсоры. Допуск пакетного поступления — до 200 мс вперёд, пропуск больше 500 мс создаёт новый якорь. Эти параметры требуют испытаний на реальном захвате и сетевом джиттере. Клиент не передаёт оплачиваемые интервалы или признак речи. Присланные «speech_start» и прочие произвольные команды не принимаются.

VAD анализирует каждый кадр отдельно по направлениям. Биллинг объединяет интервалы на общей шкале, без округления каждого фрагмента. Исходное аудио целиком, включая тишину, передаётся STT. Неудачная отправка кадра не списывает этот кадр. STT usage фиксируется после успешной отправки.

Распознанный текст приходит до запроса перевода: `{"type":"recognized","direction":"outgoing","sequence":1,"original":"...","uncertain":false}`. Перевод приходит с тем же sequence: `{"type":"translation","direction":"outgoing","sequence":1,"original":"...","text":"...","language":"en","uncertain":false}`. Sequence независим для каждого направления. Тексты существуют в памяти и передаются клиенту; в серверной базе и логах их нет. Очерёдность внутри каждого направления сохраняется независимой задачей. Сервер не синтезирует голос.

Раз в 50 кадров отправляется `{"type":"balance","balance_ms":...}`; значение включает неиспользованный резерв. Остановка: `{"type":"stop"}` от клиента либо событие сервера `{"type":"stopped","reason":"...","restore_microphone":true}`. Нет кнопки или команды паузы. Сбой провайдера, неверный кадр, отзыв устройства, исчерпание баланса и разрыв завершают звонок, возвращают неиспользованный резерв и закрывают оба STT-потока. После 15 секунд без аудиосообщений соединение останавливается; тишина должна передаваться PCM-кадрами. Через 10 минут без обнаруженной речи звонок завершается.

Ready объявляет `graceful_stop:true`. При ручном Stop сервер сразу прекращает учёт и возвращает резерв, затем ограниченно ожидает финальные тексты STT (до 2 секунд на завершение потоков и до 5 секунд на обработку результатов). Итоговый stopped содержит `transcript_complete`. При техническом сбое потоки закрываются сразу. Уже оплаченный звук и ожидание финальных текстов повторно не учитываются.

Аудиоклиент расширения реализует захват, восстановление микрофона и ручной повторный запуск. Перед WebSocket он проверяет локальные голоса и прогревает оба направления; подготовка не расходует баланс. Тексты сохраняются только локально в IndexedDB. Подробности и границы проверки — в [AUDIO_CLIENT.md](AUDIO_CLIENT.md).
